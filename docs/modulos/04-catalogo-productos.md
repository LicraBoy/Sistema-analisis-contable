# Módulo 4 — Catálogo de Productos, Ventas Diarias y Análisis y Profundidad

> Detalle movido desde CLAUDE.md (2026-10-14) sin cambios de contenido.

4. **Catálogo de Productos** (`api/catalogo_productos*.py`, `api/costeo_recetas*.py`, `api/productos_vendidos*.py`, `services/catalogo_productos*.py`, `services/costeo_recetas.py`, `services/costeo_excel_export.py`, `services/productos_vendidos*.py`, `services/comparacion_iva*.py`) — recipe costing and sales analysis, triplicated per punto de venta (`restaurante`, `cafeteria`, `carreta_mariscos`) as parallel model/service/router sets (every DB table, service, and router is a separate file per POS, never a shared parametrized table — the codebase's established convention). Independent of modules 1–3. Sub-features per POS, each with its own router mounted at `/catalogo-productos`, `/costeo`, `/productos-vendidos` (each `[-cafeteria|-carreta-mariscos]`):
   - **Catálogo**: parses the menu Excel by fixed columns (B=punto_venta, C=grupo, G=nombre, K=tipo, O=costo, Q=precio_venta, from row 6; `grupo`/`punto_venta` forward-filled since the source only writes them on change). Classification depth differs per POS and drives frontend nav depth: Restaurante has both `categoria_tipo` (Alimentos/Bebidas/Otros) and `seccion_menu` (Desayuno/Comida-Cena/Bar/Extra/Otros); Carreta de Mariscos has `categoria_tipo` only; Cafetería has neither (grouped only by `grupo`). `punto_venta` is stored as the literal source text (e.g. `"RESTAURANT"`, not `"Restaurante"`) — code that needs "the Restaurante rows" should not filter by this column with an assumed string; query it unfiltered instead (bit this cost a real bug once, see Ventas Diarias below).
   - **Costeo**: `services/costeo_recetas.py` is the one module genuinely shared across all 3 POS (`calcular_costeo`/`costeo_producto`/`costo_global_ponderado`; `pct_costo = costo / (precio_venta / iva_factor)`, `IVA_FACTOR_DEFAULT = 1.16`). Config (`ConfiguracionCosteo*`, `CosteoIncrementoGrupo*`, `CosteoPrecioSugeridoOverride*`) is per-POS and user-editable. Export uses live Excel formulas, not precomputed values.
   - **Productos Vendidos**: sales-by-product upload (`ProductoVendidoDetalle*`), fixed columns A=Producto, B=Costo, C=Venta, D=Cant., E=Tot.Costo, H=Descuento, J=Subtotal, K=Impuesto, M=TOTAL. The source file has no per-row date — only a title-row "Desde/Hasta" text describing whatever range was exported — so **Restaurante's** table is keyed by `fecha_desde`/`fecha_hasta` (a user-chosen batch range, one day or many; `POST /productos-vendidos/upload` takes both, not a `periodo` string) rather than a `YYYY-MM` `periodo` like Cafetería/Carreta de Mariscos still use (those two POS were not migrated — don't assume the same shape across POS for this table). Two saved batches for Restaurante can never overlap (upload guard checks `fecha_desde <= nueva_hasta AND fecha_hasta >= nueva_desde`, blocks until `confirmar_reemplazo=true`, then replaces only the overlapping batches) — this makes `fecha_desde` alone a safe unique batch key for the other endpoints (`GET /productos-vendidos`, `/comparar-iva`, `/export`, `DELETE`, all take `fecha_desde` not `periodo`). Rows inherit `grupo`/`categoria_tipo`/`seccion_menu`/catalog cost/price via fuzzy name-matching against the Catálogo table (`heredar_clasificacion_catalogo*`, delegates to the shared matcher in `services/matching_productos.py` for Restaurante).
   - **Cortesía**: computed directly from Productos Vendidos' own columns, no separate upload — `ingreso_real = Impuesto / 0.16`, `monto_cortesia = |ingreso_real - Subtotal|`, `cantidad_cortesia = round(monto_cortesia / Costo)` (`services/comparacion_iva.py::calcular_posibles_cortesias`, Restaurante only — Cafetería/Carreta have their own copies).
   - **Ventas Diarias** ("Inteligencia de Negocio" → Restaurante only, no Cafetería/Carreta equivalent yet): day/hour-level sales analysis layered on top of the month-level modules above. Four tabs, all under `PanelVentasDiariasRestaurante` in `CatalogoProductosPage.tsx`:
     - **Comandas Emitidas** (`models/comanda_emitida.py`, `services/comandas_emitidas.py`, `api/comandas_emitidas.py`, mount `/comandas-emitidas`) — item-level order detail (producto, mesa, fecha, hora, cuenta, cantidad, estatus), read by real header name (`services/excel_headers.py::mapear_encabezados`, accent/case-tolerant) rather than fixed position, since this file has a genuine header row — unlike almost everything else in this module. Turno (Desayuno 06:00–11:59 / Comida 12:00–17:59 / Cena 18:00–23:59 / Sin Clasificar) is computed from `Hora` via `services/turnos.py::clasificar_turno_por_hora`, since the file doesn't report its own turno.
     - **Recibos Emitidos** (`models/recibo_emitido.py`, `services/recibos_emitidos.py`, `api/recibos_emitidos.py`, mount `/recibos-emitidos`) — per-cuenta financial totals (subtotal, tax, propina, total, segmento, pagada, turno). ⚠️ Same file name as an unrelated Facturación source file (`services/facturacion.py`'s "Recibos Emitidos") — different columns, different purpose, no shared code. Unlike Comandas, this file already reports its own `Turno` (used as-is via `normalizar_turno_pos`, not recomputed from `Hora`). The raw sheet interleaves each cuenta's row with 1+ "desglose por tipo de producto" sub-rows (`Tipo`=ALIMENTOS/BEBIDAS, `Cuenta` blank) — the parser keeps only rows where `Cuenta` is non-blank.
     - Both files can cover many days in one upload (`Fecha` per row) — `POST .../upload` groups by the distinct dates found, and if any of those dates already have saved rows, responds `{"requiere_confirmacion": true, "fechas_conflicto": [...]}` without touching the DB; confirming replaces only the conflicting dates.
     - **Conciliación** (`services/conciliacion_ventas_diarias.py`, `api/conciliacion_ventas_diarias.py`, mount `/conciliacion-ventas-diarias`, `GET ?fecha=YYYY-MM-DD`) — the only piece that cross-references all of Comandas + Recibos + Productos Vendidos + Catálogo for one day, computed on the fly (no table of its own, same philosophy as Cortesía). Two independent views in the response:
       - `cuentas` (`construir_cuentas_consolidadas`): Comandas ⨝ Recibos joined by account number — Comandas' `cuenta` is a bare number ("450913"), Recibos' is `"<numero>/<codigo>"` ("450913/9A*506D"); join on the numeric prefix (`_cuenta_base`).
       - `productos` (`construir_productos_consolidados`): one row per **producto + turno** (a product ordered across two turnos gets two rows). **Money always comes from Catálogo × Comandas quantity, never from Productos Vendidos** (`costo`/`precio_venta`/`total`) — confirmed with real data that Productos Vendidos is not reliable per-product: it both omits real sales on a given day and sometimes attributes a sale to a similarly-named but distinct catalog item (real example: `HF CERVEZA BUD LIGHT LATA` in Comandas vs. `HF CERVEZA LATA PACIFICO` in Productos Vendidos, same quantity, both genuine distinct catalog rows per `catalogo_productos`). `subtotal`/`impuesto`/`descuento` and the 3 Cortesía fields *do* come from Productos Vendidos (needed since they feed the same cortesía formula Cortesía already uses) but are **prorated across a product's turno-rows** by each turno's share of that day's Comandas quantity (`_prorratear`) — summing any of these columns across a product's turno-rows reconstructs the real day total exactly; never repeat the raw day figure per row, that was tried first and is a real regression risk (protected by `tests/test_conciliacion_ventas_diarias.py`). `sin_match_productos_vendidos`/`discrepancia` flag when a product's day-total Comandas quantity doesn't match Productos Vendidos' (or is entirely absent there); `confirmado_en_historial` distinguishes "Productos Vendidos just skipped it this one day" (the product has a row in some *other* saved batch) from "never seen in Productos Vendidos at all" — the former is common and not alarming, the latter is worth real attention.
       - Because Productos Vendidos batches can span multiple days (see above) while Comandas/Recibos are always per-day, comparing one day of Comandas against a 16-day Productos Vendidos batch produced near-100% false discrepancies in practice. Fix: when the batch covering the requested `fecha` spans more than one day, the router re-queries Comandas across that **entire batch range** (not just `fecha`) before calling `construir_productos_consolidados`, and returns `"productos_rango": {"fecha_desde", "fecha_hasta"}` (else `null`) so the frontend can show a banner — `cuentas` is unaffected, always scoped to the single `fecha`.
     - Frontend: `SelectorDiasPorMes` in `CatalogoProductosPage.tsx` is a shared month-grouped day/lote picker used by all 4 tabs (normalizes each tab's own day/lote shape to `{clave, fecha, etiqueta, total}`) so the picker doesn't become one giant unbroken row as more days accumulate.
   - **Análisis y Profundidad** ("Inteligencia de Negocio" → Restaurante only, sibling of Ventas Diarias, not a tab on it — "Fase 3" of an executive BI brief; Cafetería/Carreta are excluded on principle, not just unmigrated, since they only have monthly batch-level Productos Vendidos with no per-row date, insufficient for anything here). Frontend: `PanelAnalisisProfundidadRestaurante` in `CatalogoProductosPage.tsx` owns a single `<SelectorMesAnalisis>` (`MonthPickerInput`, replaced a free date-range picker per tab after real users — gerencia/contralores — found 10 independent range pickers confusing) whose `{fechaDesde, fechaHasta}` (first/last day of the chosen month, via `primerYUltimoDiaDelMes`) is prop-drilled down to everything below; nothing under it manages its own date state. Below that, `Tabs variant="pills" color="violet"` has **5** top-level tabs — the original 10 views are grouped 1+3+3+3 to keep the top level scannable, plus a 5th standalone tab added later at the user's explicit request (breaking the "keep it to 4" goal on purpose, a deliberate exception, not a regression): `resumen-ejecutivo` (alone), `desempeno-comercial` (alone, see below), `ventas-horarios` (`PanelGrupoVentasYHorarios`: Heatmap de Ventas, Panel de Turnos, Mix de Ventas), `productos` (`PanelGrupoProductos`: Ranking de Productos, Ingeniería de Menú, Dependencia de Productos), `riesgos-alertas` (`PanelGrupoRiesgosYAlertas`: Cortesías, Oportunidades, Alertas de Riesgo) — each group is a plain nested `Tabs` (default variant, to look visually distinct from the outer pills). All child `Panel*` components (everything except `PanelResumenEjecutivo`) take `params: { fechaDesde, fechaHasta }` as a prop rather than owning a picker; the 10 original backend endpoints didn't need to change at all for this (they already accepted arbitrary `fecha_desde`/`fecha_hasta`, a full calendar month is just one more valid range).
     - **Venta neta canónica (contraloría audit, 2026-09-24):** Recibos' `total` = `subtotal + tax + propina − descuento` (verified exact against real data) and mixes in non-sales (`tipo` CORTESIA, AL COSTO, and HOTEL rows whose `segmento` starts with `CONS`/`COSTO`). Every "ventas"/"total vendido"/ticket/cuentas figure in Resumen Ejecutivo, Panel de Turnos and Desempeño Comercial now uses `services/venta_neta.py` (`venta_neta = Σ(subtotal − descuento)` over `clasificar_recibo(r) == COMERCIAL`; IVA and propina reported apart via `resumir_ventas`), user-approved definition — don't go back to summing `total`. `TUSOSA` segment (~$0.7M/4 months) is deliberately left commercial: nobody has confirmed whether it's a related party. Ranking/Optimización money is a different base (Catálogo price × Comandas, doesn't reconcile to Recibos, 8–24% apart on real data, cause unknown) — Resumen Ejecutivo's `conciliacion` block (`construir_conciliacion_ventas`, collapsed `TarjetaConciliacionVentas` in the UI) quantifies that gap plus comandas-without-recibo, sin-precio and duplicate-price products; it never explains the cause. "Día" comparison is vs. the same weekday of the previous week and flagged `parcial` when the last day has <70% of the average day's cuentas.
     - **Catálogo matching performance/determinism:** `matching_productos.py` builds a pre-normalized index once per catalog list (single-slot cache validated by list identity + length) — was ~2 s per 700 products (re-normalizing 1,526 names per product), now ~10 ms. The catalog has duplicate names with different prices (e.g. `BAHAMA MAMA` 110/104); ties break deterministically: the comanda's own `grupo` (`grupo_preferido`), then higher `precio_venta`, then alphabetical grupo — never DB order. `clasificar_producto_contra_catalogo_detallado` also returns `ambiguo`; ranking rows carry `precio_ambiguo`/`sin_precio`. Any new caller that has a comanda `grupo` should pass it so Ranking/Turnos/Mix agree.
     - **Design principles established across this phase — don't relitigate without reason:** (1) aggregate business-level money (KPIs, totales, propina) always comes from Recibos Emitidos, never reconstructed (as venta neta, see above); (2) per-product money (ranking, márgenes, Conciliación) always comes from Catálogo × Comandas Emitidas quantity via `services/matching_productos.py::clasificar_producto_contra_catalogo`, never Productos Vendidos (PV misattributes quantity/name between similar products with real data — see Conciliación above); (3) PV is batch-ranged, not per-day, so every panel that needs to cross it against a day/turno breakdown first checks whether the covering lote is single-day (`fecha_desde == fecha_hasta`) — multi-day lotes only contribute to totals, never to day/turno splits, and the frontend is always told how many lotes got excluded rather than faking precision; (4) no insight is emitted from an insufficient sample (e.g. mejor/peor día de semana requires ≥2 distinct weekdays with ≥2 samples each) — same caution repeated in Resumen Ejecutivo, Heatmap, and Oportunidades; (5) each `services/*.py` in this phase is pure and DB-free (takes already-loaded SQLAlchemy model lists, no queries of its own) — the router does the querying and calls the service, mirroring `tests/test_conciliacion_ventas_diarias.py`'s `_comanda()`/`_recibo()`/`_pv()`/`_catalogo()` constructor-without-persisting pattern that every new `tests/test_*.py` here follows too.
     - **Desempeño Comercial** (`services/desempeno_comercial.py`, `api/desempeno_comercial.py`, mount `/desempeno-comercial`) — Contraloría/Gerencia-facing, compares the chosen month against the **equal-length** previous period (`services/rangos_fecha.py::periodo_anterior` — reused verbatim, not reimplemented) across 10 sections: KPI deltas (ventas/cantidad/ticket/cuentas), quick top-3 impulsores positivos/negativos, full comparativo por grupo/categoría/sección (reuses `ranking_productos.py::construir_ranking_grupos` and `mix_ventas.py::construir_mix_categoria_tipo`/`construir_mix_seccion_menu` for **both** periods, then a new generic `construir_comparativo_dimension(actual, anterior, clave)` merges them — same function serves grupo (`clave="grupo"`) and categoría/sección (`clave="etiqueta"`, mix_ventas' own field name)), top 5 ganadores/perdedores, productos nuevos, participación de ventas (reuses `pct_participacion` already on `construir_ranking_grupos`'s output), and auto-generated hallazgos (same `{tipo, mensaje, tono, accion_sugerida}` shape as Resumen Ejecutivo/Oportunidades, for UI consistency — the spec itself didn't ask for `accion_sugerida` but every other insight/alert list in this module has one). `construir_productos_comparados(productos_actual, productos_anterior)` is the one piece of real new logic: matches products by name across the union of both periods — products with revenue in both periods go to `comparados` (including ones that vanished entirely, `ingreso_actual=0`, so discontinued products still show up as real "perdedores" instead of silently disappearing); products with revenue only in the current period go to a separate `nuevos` bucket and are **excluded** from `comparados`/top ganadores/perdedores everywhere, including the quick Sección 2 view — a brand-new product isn't "growth" of something that already existed, and mixing it in would produce a misleading ranking (explicit, deliberate exclusion, not an oversight). Reuses `dependencia_productos.py::construir_tabla_dependencia`'s `top5_pct` as-is for the "top 5 productos = X% del ingreso" hallazgo instead of recomputing a Pareto. No new backend aggregation was needed beyond this comparison layer — every per-period building block already existed from earlier phases. Frontend `PanelDesempenoComercial` is itself a small nested `Tabs` (2 sub-tabs, default variant) rather than a single flat panel: **Resumen** (`PanelDesempenoComercialResumen`, the 10 sections above) and **Optimización de Precios** (see next).
     - **Optimización de Precios** (`services/optimizacion_precios.py`, second route on the *same* `api/desempeno_comercial.py` router — `GET /desempeno-comercial/optimizacion-precios`, same "sub-view = extra route on one router file" convention as `resumen_ejecutivo.py`'s `/tendencia-mensual`) — a rentabilidad/costeo analysis over the **entire** matched catalog (not just "REQ AJUSTE": `estado` highlights, it doesn't filter — a v1 of this feature filtered to REQ AJUSTE only and was revised at the user's explicit request, "el análisis deja de enfocarse en el producto individual y empieza a enfocarse en cómo cada grupo, categoría y sección afecta el porcentaje de costo global del restaurante"), presented with the exact same Sección → Categoría → Grupo → Tabla navigation as Catálogo/Ranking de Productos (frontend mirrors `RankingPorCategoria`/`RankingPorGrupo`/`RankingTablaProductos` verbatim, reusing `SECCIONES_MENU`/`CATEGORIAS_TIPO`). For every product with the month's sales data, calls `costeo_recetas.py::calcular_costeo` directly (same pure function the Costeo tab itself uses — **not** reimplemented, so the OK/REQ AJUSTE threshold and precio-sugerido formula can never drift between the two features). All money is **IVA-exclusive** — "Subtotal Actual"/"Subtotal Potencial" (`ingreso_bruto / iva_factor`) and `incremento_potencial` are computed on subtotal, never on gross ingreso, since "el IVA no representa utilidad para la empresa" (`iva_actual = ingreso_bruto - subtotal_actual` is shown separately). `construir_resumen_por_dimension(productos, campo, pct_costo_objetivo)` is one generic function called 3 times (`seccion_menu`/`categoria_tipo`/`grupo`) to build the resumen card shown at each level of the hierarchy before drilling into the next — `pct_costo_promedio` is weighted by volume (same criterion as `costeo_recetas.py::costo_global_ponderado`), never a simple average of percentages; `incremento_potencial_estimado` at any level only sums "REQ AJUSTE" products (it's "opportunity," doesn't apply to already-healthy ones). **`pct_costo_objetivo` is a single global value shown identically at every product/group/section** — `ConfiguracionCosteo` has no per-group objetivo today, and the user explicitly chose "show the same global %" over adding new configuration scope when this was flagged. The headline KPI is `incremento_potencial_total` (sum of `incremento_potencial` across all "REQ AJUSTE" products only). `GRUPOS_HORA_FELIZ` (the 5 literal `"HORA FELIZ ..."` grupo values) is a deliberately narrower subset of `catalogo_productos.py::GRUPOS_BAR` (which also includes ordinary cervezas/vinos/licores); `construir_comparacion_hora_feliz` compares its weighted `pct_costo_promedio` specifically against the literal grupo `"CERVEZAS"` (confirmed with the user — not "the rest of the Bar section"), deriving `margen_pct = 100 - pct_costo_promedio` (valid because `pct_costo` is already computed on subtotal, same as `calcular_costeo`) — either side returns `None`, never a fabricated 0, if that side has no matched products.
     - **Resumen Ejecutivo** (`services/resumen_ejecutivo.py`, `api/resumen_ejecutivo.py`, mount `/resumen-ejecutivo`) — the one tab that still manages extra local state on top of the shared month: a `SegmentedControl` toggles between "Por mes" (KPIs — total vendido, ticket promedio, cuentas, piezas, propina, % variación vs. periodo anterior — + a daily-trend chart (Recharts) + up to 6 auto-generated insights, each carrying a `tipo` (drives a per-type icon in the frontend, `TIPO_INSIGHT_ICONO`; icon shown alongside the plain `IconBulb` used for `accion_sugerida`), `accion_sugerida`, and a tone (positivo/negativo/neutral), + a "Comparación contra periodo anterior" card with 4 side-by-side deltas: día/semana/mes/año, from `services/resumen_ejecutivo.py::construir_comparaciones_periodo`) and "Todos los meses" (ignores the shared month entirely; calls `GET /resumen-ejecutivo/tendencia-mensual`, a second route on the same router with no date params, backed by `construir_serie_mensual` — one bar per calendar month across all loaded history). Reads only Comandas + Recibos for KPIs — deliberately skips Productos Vendidos since it's batch-based and doesn't fit an arbitrary date range. One insight, `_insight_precio_candidato` (`tipo: "precio_candidato"`), does need per-product data: it flags products in the top quartile of `cantidad` **and** with `margen_pct` below the range average (same cuartil/promedio convention as `oportunidades_comerciales.py::_detectar_productos_desaprovechados`, inverted — that one wants low popularity + high margin, this wants the opposite) as candidates worth a price review; it deliberately never proposes a specific % increase or a profit projection (the system has no way to know how demand would react) — the router now also calls `construir_ranking_productos(comandas, catalogo)` to get that data, threaded into `generar_insights`'s new `productos` parameter.
     - **Heatmap de Ventas** (`services/heatmap_ventas.py`, `api/heatmap_ventas.py`, mount `/heatmap-ventas`) — grid of exact-date rows (one row per calendar date with data, up to ~31 for a full month) × 06:00–23:00 hour columns (Comandas' `hora`, order time — not Recibos' checkout time), each cell = raw `piezas` for that exact date+hour. **Deliberately not averaged/combined by day-of-week** — an earlier version grouped all Mondays of the month into one averaged row, which the user found confusing (couldn't tell "Mon the 7th" from "Mon the 14th"); every date is now its own row, sorted chronologically, labeled `"{Lun|Mar|...} {día del mes}"` (e.g. "Lun 7", "Lun 14") on the frontrend via `etiquetaFechaHeatmap`/`diaSemanaDesdeFecha` (computed from the ISO date string, Monday=0..Sunday=6 — deliberately never mixed with JS's native `Date.getDay()` Sunday=0 convention, a real bug hit once). Response shape: `celdas: [{fecha, dia_semana, hora, piezas, top_productos}]` + `fechas_con_datos: string[]` (all comanda dates, even ones with no cells because their activity fell outside 06:00–23:00 — used to render an otherwise-empty row rather than silently dropping that date). `top_productos` includes **all** products ordered in that exact date+hour, sorted descending by cantidad with an alphabetical tie-break for determinism (no cap — a past `_MAX_TOP_PRODUCTOS = 3` limit was removed on request). The hover `Tooltip` only shows the piezas/summary line (a "clic para ver productos" hint) — it deliberately does **not** repeat the product list (an earlier version did, which read as a confusing "black box" duplicating the click panel and was removed); clicking a cell pins it (`celdaSeleccionada` state keyed by `{fecha, hora}`, cell gets a violet `outline`) and renders its full product list as a real table (`ESTILO_ENCABEZADO_TABLA`-styled) in a fixed panel below the grid, inside the same `Card` — no modal. **`oportunidades_comerciales.py::_detectar_horas_muertas` depends on this shape**: since the heatmap no longer pre-aggregates by day-of-week, that detector now does its own dia_semana/hora re-aggregation internally (averaging `piezas` across the dates in `celdas` that share a `dia_semana`) before applying its "hora muerta" threshold — a reminder that any further heatmap shape change must also be checked against this consumer, which calls `construir_heatmap_dia_hora` in-process (no HTTP). **Picos de venta**: `services/heatmap_ventas.py::detectar_picos_venta(celdas)` flags a cell as a "pico" when its `piezas` is ≥50% (`_UMBRAL_PICO_PCT_SOBRE_PROMEDIO`) above the average `piezas` of that same `hora` across the *other* dates in the month (needs ≥2 other dates to compare against, `_MIN_FECHAS_PARA_COMPARAR`, else skipped — no pico from a single reference point) — this is pure statistical outlier detection, the system cannot infer a real-world cause (e.g. "fiesta mexicana") on its own. To capture the real cause when the user knows it, there's a tiny new persisted model, `NotaFechaHeatmap` (`models/nota_fecha_heatmap.py`, table `notas_fecha_heatmap`, one row per `fecha` unique) — `PUT /heatmap-ventas/notas` upserts a note by date (blank note deletes the row instead of storing an empty string), and the main `GET /heatmap-ventas` response includes both `picos: [...]` and `notas: {fecha: texto}` for the requested range. Frontend: pico cells get an orange border in the grid (distinct from the violet selection outline), a "Picos de venta detectados" section lists them with their driving products and any saved note, and the click-panel gained a `NotaFechaHeatmapInput` (remounted via `key={fecha}` on fecha change instead of a `useEffect`, so its local state always starts from that date's saved note). The click-panel's product list was also redesigned from a plain Producto/Cantidad table to `ListaProductosBarra` — rank badge + proportional bar (width = `cantidad / max`) + count, same visual language as the grid's own color-intensity encoding.
     - **Ranking de Productos** (`services/ranking_productos.py`, `api/ranking_productos.py`, mount `/ranking-productos`) — criterio Popularidad/**Menos vendidos** (frontend-only: same `cantidad` field, ascending instead of descending — no backend change)/Margen/Ingreso/En declive, with `agregar_variacion_periodo_anterior`/`agregar_variacion_periodo_anterior_grupos` comparing quantity/ingreso vs. the immediately preceding period (`None` when the product/group is new, never a fake "-100%"). `construir_ranking_productos` also returns each product's `categoria_tipo`/`seccion_menu` (from `clasificar_producto_contra_catalogo`, `None` on no catalog match) — added specifically so the frontend can reuse Catálogo's own 3-level navigation. Joins Comandas × Catálogo; deliberately does **not** filter by `punto_venta` (`catalogo_productos.punto_venta` doesn't come through as a clean `"Restaurante"` string) — don't "fix" this expecting Restaurante-only filtering. `construir_ranking_grupos` also computes `pct_participacion` per group (ingreso share of all groups), reused by Mix de Ventas and the Resumen Ejecutivo diagnostic below. **Frontend navigation now mirrors Catálogo exactly** (no more flat table + Por Producto/Por Grupo toggle): `PanelRankingProductos` → `RankingPorCategoria` → `RankingPorGrupo` → `RankingTablaProductos`, reusing Catálogo's own `SECCIONES_MENU`/`CATEGORIAS_TIPO` constants and `ESTILO_ENCABEZADO_TABLA` header style verbatim (not duplicated) — the one difference from Catálogo's `PanelPorCategoria`/`PanelSubgrupos` is a "Sin Clasificar" bucket at both the sección and categoría level, needed because Ranking rows come from Comandas and can lack a catalog match (Catálogo's own rows never do, so it has no such bucket) — and no "Noches Temáticas"/"Días Especiales" special-casing (`dia_tematica`/`evento_especial` don't exist on `RankingProductoFila`). Group cards are sorted by, and show, the metric matching the active criterio (`metricaGrupoRanking`: avg margen_pct, or summed cantidad/ingreso_total) instead of Catálogo's plain alphabetical order. `colorMargenPct` (inverse of `colorPorcentajeCosto`: high margin = green) colors the Margen % column; the table shows **all** matched products (a past `.slice(0, 20)` cap was removed).
     - **Ingeniería de Menú** (`services/menu_engineering.py`, `api/menu_engineering.py`, mount `/menu-engineering`) — classifies each product into 4 quadrants (Estrella/Caballo de Batalla/Rompecabezas/Perro) combining popularity (`cantidad`, cut at the median) and profitability (`margen_pct`, cut at the mean) — reuses `ranking_productos.py::construir_ranking_productos`'s output directly, no new querying. Products without a catalog match (`margen_pct is None`) go to `sin_clasificar`, never a guessed quadrant. Needs ≥4 matched products to classify anything.
     - **Panel de Turnos** (`services/panel_turnos.py`, `api/panel_turnos.py`, mount `/panel-turnos`) — Desayuno/Comida/Cena comparison: total vendido (Recibos), ticket promedio, piezas, % participación, and `margen_pct` (Catálogo × Comandas per turno, cached per product). Reads Comandas + Recibos + Catálogo via the shared `services/turnos.py::RANGOS_TURNO` boundaries.
     - **Mix de Ventas** (`services/mix_ventas.py`, `api/mix_ventas.py`, mount `/mix-ventas`) — sales distribution (% participación) by grupo, `categoria_tipo`, `seccion_menu` (all real `CatalogoProducto` columns) and turno. Grupo reuses `construir_ranking_grupos`; turno reuses `panel_turnos.py::construir_comparativo_turnos` verbatim; `categoria_tipo`/`seccion_menu` needed their own aggregation loop (`mix_ventas.py::_construir_mix_por_dimension`) since `ComandaEmitidaDetalle` doesn't carry those fields itself — only the Catálogo match does (`services/matching_productos.py::clasificar_producto_contra_catalogo`).
     - **Cortesías — fuente principal = Recibos Emitidos** (added 2026-09-24): `construir_cortesias_desde_recibos` (`tipo = CORTESIA`, monto = subtotal − descuento, sin IVA/propina; response key `recibos`) covers every month and breaks down by `segmento` (= the department that consumed), turno, día and top-10 cuentas; it matched Productos Vendidos within ~0.4% where both exist (ago $47,270 vs $47,283). Productos Vendidos is now only the per-product detail below it — its Impuesto column is empty for jun/jul 2026, which used to leave those months blank. `elegir_resumen_cortesias` feeds the Alertas de Riesgo "incremento de cortesías" alert from Recibos only when BOTH periods have recibos, else falls back to PV (never mixes sources). Real-data caveat worth a contralor's eye: "COSTO CAFETERIA PAN Y OTROS" is ~half of jul/ago cortesías, probably an internal cost transfer rather than a guest courtesy. The PV-based section below (unchanged):
     - **Cortesías (PV detail)** (`services/cortesias_dashboard.py`, `api/cortesias_dashboard.py`, mount `/cortesias-dashboard`) — reuses `services/comparacion_iva.py::calcular_posibles_cortesias` and `services/conciliacion_ventas_diarias.py::construir_productos_consolidados` rather than reimplementing either. Total economic impact + per-product ranking; day/turno breakdown only for single-day PV lotes, with a `dias_excluidos_por_lote_multi_dia` counter surfaced to the frontend. Reads Productos Vendidos (same overlap-inclusive date filter as the upload guard) + Comandas (turno breakdown) + Catálogo.
     - **Dependencia de Productos** (`services/dependencia_productos.py`, `api/dependencia_productos.py`, mount `/dependencia-productos`) — full Pareto/concentration table (rank, % individual, % acumulado por producto, sorted by `ingreso_total` desc, ties broken alphabetically for determinism), plus `top5_pct`/`top10_pct` callouts. `oportunidades_comerciales.py::_detectar_concentracion_ventas` already does a partial version of this (pass/fail at a 70% threshold) but exposes no reusable table — this service is the one place that materializes the full cumulative curve; needs ≥5 products with `ingreso_total > 0` to compute anything.
     - **Oportunidades Comerciales** (`services/oportunidades_comerciales.py`, `api/oportunidades_comerciales.py`, mount `/oportunidades-comerciales`) — doesn't query the DB directly; calls the Heatmap and Ranking service functions in-process and layers named-threshold rules on top (horas muertas <20% del pico, productos desaprovechados por cuartil, concentración Pareto >70% en top 20%, grupos <30% del promedio, declive fuerte ≤-30%) — changing those two services' output shape breaks this silently. Each opportunity carries a severidad (alta/media/baja), `accion_sugerida`, and now a `dia_semana: int | None` field — only `hora_muerta` sets it (an actual weekday, since only that detector is day-specific); the other 4 types always carry `None`. `detectar_productos_en_declive` (no leading underscore, deliberately public) is reused as-is by Alertas de Riesgo below rather than duplicated. Frontend `PanelOportunidades` groups by this field: a "General" section for `dia_semana === null` items, then one section per weekday that has at least one `hora_muerta` opportunity — replaced the old flat card list.
     - **Alertas de Riesgo** (`services/alertas_riesgo.py`, `api/alertas_riesgo.py`, mount `/alertas-riesgo`) — same rules-over-aggregated-data role as Oportunidades, always comparing against the immediately preceding period of equal length. "Producto estrella cayó >30%" delegates straight to `oportunidades_comerciales.detectar_productos_en_declive` (same `_UMBRAL_DECLIVE_FUERTE_PCT`, not duplicated); "grupo con tendencia negativa" uses the new `ranking_productos.py::agregar_variacion_periodo_anterior_grupos`; "incremento de cortesías" diffs two `cortesias_dashboard.py::construir_resumen_cortesias` calls (current vs. prior period); "disminución de margen" uses the new `alertas_riesgo.py::agregar_variacion_margen` (points-based diff, not %, since a margin move from 40% to 34% is 6 points, not "-15%"). Every "no prior data" case yields no alert, never a fabricated one (same convention as `agregar_variacion_periodo_anterior`).
     - "Periodo anterior" for these routers (`resumen_ejecutivo.py`, `ranking_productos.py`, `oportunidades_comerciales.py`, `alertas_riesgo.py`) is computed by the shared `services/rangos_fecha.py::periodo_anterior(fecha_desde, fecha_hasta)`: if the given range is exactly one calendar month, it returns the previous calendar month (correct for the common case now that the frontend always sends a full month — a day-count window would otherwise land mid-month, e.g. 30 days back from Sept 1 is Aug 2, not Aug 1); for any other range it falls back to the original same-length-immediately-before logic, so nothing that ever called these routers with an arbitrary range regresses. `rangos_fecha.py::mismo_periodo_anio_anterior` (shift both ends back one year, Feb 29 clamped to the 28th) is the other half, used only by Resumen Ejecutivo's "año" comparison.
     - Maps to the original brief questions: días mejor/peor + why → Resumen Ejecutivo (includes an auto-generated cause insight comparing that weekday's turno/grupo mix against the range average, gated by the same `_UMBRAL_BRECHA_PARTICIPACION_PCT` significance threshold); horarios más rentables → Panel de Turnos (`margen_pct`); productos que impulsan ventas / perdiendo demanda → Ranking ("En declive" criterio) and Ingeniería de Menú; grupos con más ingreso / qué sostiene las ventas → Ranking "Por Grupo" and Mix de Ventas; dependencia de pocos productos → Dependencia de Productos; productos con más cortesías → Cortesías; oportunidades comerciales → Oportunidades; riesgos ejecutivos → Alertas de Riesgo; acciones concretas → `accion_sugerida` on insights/opportunities/alerts.
     - Deliberately **not** built, not forgotten: cross-POS comparison (Cafetería/Carreta have no day/hour data to compare with); forecasting/ML/predictive sales; a "product funnel" (concept was never defined with the user).
     - The original free date-range picker (`DatePickerInput type="range"` + per-tab quick-range buttons) was replaced entirely by the single month selector above — gerencia/contralores found 10 independent range pickers with arbitrary start/end dates too much freedom/information. There is no longer a way to pick an arbitrary multi-day range in this section; a calendar month (or, in Resumen Ejecutivo, "todos los meses") are the only two shapes of query it sends.
