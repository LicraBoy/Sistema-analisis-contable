# Módulo 5 — Amarre de Costo de Ventas

> Detalle movido desde CLAUDE.md (2026-10-14) sin cambios de contenido.

5. **Amarre de Costo de Ventas** (`api/amarre_costo.py`, `services/amarre_costo_parsing.py`, `services/amarre_costo_reportes.py`, `services/amarre_costo_workbook.py`, `services/amarre_costo_storage.py`, `models/amarre_costo_periodo.py`) — hotel inventory reconciliation for Torres Mazatlán, replacing a manual monthly Excel ("Amarre de Costo de Ventas"). Independent of modules 1–4. Each month the user uploads 12 raw Novohit export files (one per warehouse/report type: balanza, 4 physical-count reports `INV030`, 2 despacho/salidas reports `INV110`, 5 entradas/compras reports `INV160`) via `POST /amarre-costo/{periodo}/upload/{tipo}` (`tipo` is one of the 12 fixed slugs in `TIPOS_VALIDOS`/`TIPOS_ARCHIVO_AMARRE_COSTO`), in any order, each updating only its own fields on a per-`periodo` (`YYYY-MM`) snapshot row (`AmarreCostoPeriodo`) — never touching another file's fields or the manually-captured "hueco" fields. Each upload is also saved to disk (`amarre_costo_storage.py`, same on-disk-not-BLOB pattern as `facturacion.py::guardar_adjunto_factura`, tracked per-type in `AmarreCostoArchivoOriginal`) — needed by the export (see below), not just parsed.

   **Critical parsing design**: unlike every other module's fixed-column-position convention, these Novohit reports are hierarchical and change size every month (however many items got counted/purchased that month), so `amarre_costo_parsing.py` locates every total by searching for its literal **label text** (e.g. `"TOTAL TABAQUERIA"`, `"Sub Total:"`, `"TOTAL GENERAL DE ENTRADAS"`) rather than any fixed row/cell reference — replicating a real Excel workbook the user had that hard-coded row-specific SUM formulas (`=AD1494+AD1794+...`) which had to be manually re-pointed every month is exactly the busywork this module eliminates. Physical-count reports (`INV030`) nest 3 levels (categoría → subcategoría → artículos), each closed by its own `"TOTAL <nombre>"` row; only the level-1 (categoría) row is real — distinguished from subcategory rows by a leading non-breaking space (`\xa0`) that subcategory totals always carry and category totals never do (`_es_total_nivel1`). A category name can legitimately appear more than once in one file (e.g. "Alimentos"/"Bebidas" split across unrelated areas of the warehouse) — `_totales_nivel1` **sums all occurrences**, confirmed against real data (Restaurant-Bar's "Alimentos" = 3 separate `TOTAL ALIMENTOS` rows summed). Money in `INV030`/`INV110` total rows is stored as **text with commas** (`"16,189.85"`), unlike individual item rows which are real floats — `_es_celda_numerica`/`_numeros_en_fila` handle both. Every "por texto" function has a "por coordenada" twin (`localizar_*` in the same file) that returns the `(fila, columna)` where a value was found instead of the value itself — used only by `amarre_costo_workbook.py` (see below) to write Excel formulas pointing at that exact cell, not by the Python-side report builders.

   Validated end-to-end against the real files in `INVETARIOS/` (checked into the repo root, one real month — agosto 2026 — with both the 12 source files and the original hand-built master workbook to diff against): balanza, all 5 entradas files, and all 9 salidas/despachos values match the known-correct master-workbook numbers exactly. Two nuances caught only by diffing against the real master workbook cell-by-cell, not by spot-checking: (1) `parsear_salidas_almacen_general`'s `despacho_gasto`/`despacho_centro_costo` are the **raw** label values, not the "Despacho a Gasto" figure `2DATOS ENTRYSAL!D8` actually displays (`despacho_gasto − despacho_centro_costo`) — every consumer must do that subtraction itself, `construir_datos_entrysal` and `_construir_hoja_entrysal` both do; (2) Almacén General's own "salidas" total in `Amarre COSTO` (`_linea_alm_gral`) is `despacho_gasto + despacho_mtto − ent_mtto_subtotal`, not the more intuitive-looking `despacho_gasto − despacho_mtto + traspasos_a_satelites` (an earlier version used that formula and was off by tens of thousands of pesos — the departmental-traspasos term cancels algebraically against `despacho_centro_costo`, it doesn't add). A handful of physical-count categories (Ropa y Uniformes/Almacén General, Artesanías/Tienda, Alimentos/Cafetería) are **deliberately left unmapped** (return 0.0) rather than guessed, because the real master workbook computed them from ad-hoc single-cell references, not a clean category total — each is flagged with an inline comment naming the real expected value, for whoever calibrates them against a second real month.

   Reports/output: `construir_amarre_costo` reproduces the real "Determinación del Costo de Ventas" block per warehouse (inventario inicial + entradas − salidas/traspasos = inventario en libros, compared against the physical inventario final — note the sign convention: for Almacén General, "salidas" are outflows to the satellite warehouses and get **subtracted**; for the satellite warehouses (Restaurant/Bar/Cafetería/Tienda) that same transfer is a receipt and gets **added**, confirmed against real formulas), plus an editable "Mercancía en Consignación / No Forma Parte del Inventario" line-item list (`AmarreCostoConsignacionRenglon`, variable length, CRUD via `POST/PATCH/DELETE .../consignacion`). Known real huecos with no source in any report (nullable columns, never silently defaulted to 0, only ever set via the whitelisted `PATCH /amarre-costo/{periodo}/manual`): `inv_final_mantenimiento`, `entrysal_cafeteria_bebidas` (Cafetería has no "Bebidas" line in the despachos report), `resumen_lavanderia` (Fichas de Lavandería).

   **Export (`GET /amarre-costo/{periodo}/export`) is a full clone of the original 15-sheet master workbook with live Excel formulas, not a computed-values summary** — the user explicitly rejected a first version that exported only the 3 result sheets with static numbers ("quiero que el Excel genere tal cual como está el archivo... con todas las fórmulas, igualito"). `amarre_costo_workbook.py::generar_workbook_amarre_costo` re-reads each stored original file, pastes it verbatim into a sheet with its real name (`1BALANZA`, `3ALM GRAL`, `3TIENDA`, `REST-BAR`, `CAFETERIA 1`, `SAL ALMACEN GRAL`, `SAL MTTO`, 5× `ENT *`), appends a "Gran Total" table under each physical-count sheet whose Monto cells are **formula strings built from the `localizar_*` coordinates found that month** (e.g. `=AE1494+AE1794+AE2112+AE2134`, mirroring the real workbook's `=AD1494+AD1794+...` pattern but regenerated automatically instead of hand-edited), then writes `Amarre COSTO`/`2DATOS ENTRYSAL`/`4Resumen INV` as formulas referencing those pasted sheets and Gran Total cells — so the exported file recalculates live in Excel if the user edits a pasted cell, without reintroducing the "reajustar la fórmula cada mes a mano" problem the module was built to eliminate. `4Resumen INV` is rebuilt at its real cell layout (per-concept rows 8-17 / 20-27 / 36-38 / 42-43 with account codes, block subtotals, Tienda extras 29-33, cross-check rows 45-51 that must be ≈0). Deliberately simplified vs. the original: no `SUBSTITUTE`/`VLOOKUP`/`IFERROR` account-code lookup for the Concepto column (cosmetic only, doesn't affect any figure) — concepts are written as plain text. The 3 categories with no reliable automatic mapping (see above) become a manual-input cell (yellow fill, cell comment pointing at the pasted sheet) instead of a wrong formula. No LibreOffice is installed in this dev environment, so formula correctness is verified with a small in-repo formula evaluator (`+`/`-`/`SUM(range)`/cell-refs only, which is all this module ever generates) rather than an actual recalculation — see `tests/test_amarre_costo_workbook.py`. Periods uploaded before this export existed have no stored original file and must be re-uploaded before they can be exported (the endpoint 400s with a clear message naming which `tipo`s are missing).

   Frontend: standalone `pages/AmarreCostoPage.tsx`, a `MonthPickerInput` period selector driving 12 grouped upload dropzones (Balanza/Conteos Físicos/Salidas/Entradas) plus 3 report tabs (still Python-computed, for quick on-screen review — only the Excel export is the full live-formula clone).
